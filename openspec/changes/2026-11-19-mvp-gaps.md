## P0 — 动工前必须定（影响 parser / 状态机 / 动作模型）

### 1. 单击延迟与手势互斥策略（未定义）

**问题**：`call:click` 与 `call:double` 同时存在时，一次单击必须等到双击窗口（500ms）结束才能判定，
用户感知就是"按键迟滞半秒才生效"。所有 spec 都没写这条。

**影响**：parser 的核心状态机设计；直接决定"手感"。

**建议规则**：
- 若该物理键**已绑定 double 规则** → 单击必须等待双击窗口结束再判定（延迟 = `double_click_ms`）。
- 若**未绑定 double** → 单击在 release 时立即判定，不等待。
- 长按在达到阈值时**立即**触发（不等 release），且这次按压的 release 不再产出 click。
- 配置项 `ui.show_latency_hint` 可在事件流标注 `(waited double window)`，方便用户理解延迟。

### 2. 原始按下/松开事件 + 按住式 PTT（`ptt_hold`）

**问题**：remote-mic-app 的王牌是**按住说话**（press-to-talk），松开即停。
我们的动作模型只有 `ptt_toggle`（按一下开、再按一下关），并且 device-input 只对外产出聚合后的 `trigger`，
**没有 press/release 边沿**，所以做不出按住说话。

**影响**：动作模型、事件模型、parser 输出。

**建议规则**：
- device-input 增加内部边沿事件（不进 UI 事件流，供 parser / executor 内部使用）：
  `edge press key=<mute|call|volp|volm>` / `edge release key=<...>`
- 新增动作 `ptt_hold`：在 `press` 时开麦推流，在 `release` 时停麦；中途离开 learn 模式或蓝牙断连时**强制停麦**。
- `call:click` 若绑定 `ptt_hold`，需要说明语义模糊（单击 = 按一下就松开会立刻结束），建议 `ptt_hold` 只绑定到长按或长按住类交互；spec 里给出推荐用法表。

### 3. 系统默认行为抑制（"拦截"其实拦不住）

**问题**：这是最容易被误解的一点。AVRCP 音量键与媒体键由 BlueZ + 音频服务直接消费，
**我们能在 D-Bus 上"看到"事件，但无法阻止 PulseAudio/PipeWire 把音量改掉**；
`call:click` 在非通话状态等价于 play/pause，系统媒体也会照常响应。
所以 "把按键改成自定义功能" 在纯用户态下是"并存"而非"独占"。

**影响**：产品承诺与用户预期；需要在 spec 与 UI 里如实说明，并给出可选缓解手段。

**建议选项（三选一，需你拍板）**：
- A（推荐，MVP）：**承认并存**。默认把自定义绑定优先放在 `volp:long`、`volm:click`、`call:long` 这类系统默认行为较弱/较无害的触发上；
  界面与文档明确声明"AVRCP 音量键仍会改变系统音量"。实现成本最低，行为可预期。
- B（部分抑制）：检测到音量变化后用 `pactl set-sink-volume` 回滚到映射前值。可行但有音频抖动、与用户手动调音量冲突，需开关项，默认关。
- C（彻底独占）：不用系统蓝牙栈，自建 AVRCP/HFP 端点接管。工作量极大，MVP 明确不做。

### 4. 未知报文提示（逆向新按键的抓手）

**问题**：学习模式只对已知 trigger 给反馈。如果用户按了某个键、耳机也发了报文、但我们的 parser 不认识，
界面是**完全沉默**——用户无法区分"硬件不上报"和"我们没解析出来"，调试会走进死胡同。

**影响**：learn-mode 的可诊断性，直接影响 Phase 3 抓包标定效率。

**建议规则**：
- 收到无法映射为已知 trigger 的报文 → learn 模式下输出
  `> [LEARN ⚠] unknown pdu: <cid/opcode 摘要>`（normal 模式静默或仅在 debug 日志）。
- 配 `test` 之外的新命令 `debug on|off` 打印原始报文摘要（默认 off）。

## P1 — 建议纳入 MVP（成本小、收益明确）

### 5. `doctor` 自检命令
一键检查：蓝牙适配器与权限、目标设备是否在线、HFP 是否被系统占用、uinput 可用性（`/dev/uinput` 权限）、
PulseAudio 虚拟麦设备是否存在、OBS WebSocket 是否连通、忙灯是否可控。
输出逐项 ✅/❌ 与修复建议。**避免用户把环境问题误判为程序 bug**。

### 6. PTT 音频源选择（配置项缺失）
`ptt` 到底把**耳机麦克风**还是**本机麦克风**送进虚拟麦，spec 没定义。
建议配置 `actions.ptt.source: headset | local | default`，默认 `default`（系统默认输入）。
伴生规则：进入 PTT 时若输入设备被拔出 → 停麦并报 ERR，不静默失败。

### 7. 单实例锁 + 资源清理
两个实例同时跑会抢蓝牙监听、抢虚拟麦、抢 uinput。
建议：`/tmp` 或 `$XDG_RUNTIME_DIR` 下的 PID 锁文件，重复启动直接退出并提示；
`quit` / SIGTERM / SIGINT 统一走清理路径（停采集 → 停 PTT → 恢复终端 → 释放 uinput / 写回未保存规则提示）。

### 8. 日志落盘与事件流导出
`--log <path>` 把事件流（含 EVENT/ACTION/STATE/ERR）以行格式写入文件，
并与非 TTY 降级模式复用同一输出通道；支持 `export feed` 导出最近 200 行为文本，方便贴给我做分析。

### 9. 配置变更检测
外部编辑 `config/rules.json` 后是否热重载。建议：**检测 mtime，发现变化则提示 `config changed externally, 输入 reload 生效`**，
新增 `reload` 命令；不做静默自动重载（避免覆盖用户内存中的未保存改动）。

## 硬件待验证（不是功能，但会改写功能边界）

在 `docs/蓝牙调试指南.md` 的采样表之外，还有 4 个未知项，抓包时顺手确认：

1. `mute` 键是否有**长按 / 双击**变体？（若有，触发源要从 7 个扩到 9 个）
2. `volm`（音量-）是否存在长按？（目前只按单击处理）
3. `call` 键在**空闲非通话**状态是否上报（用于 play/pause）？若无，则 `call:click` 实际上是"仅通话可用"，与 `mute` 同级受限。
4. 忙灯是否**可写**（能否由主机指令点亮/闪烁），这直接决定 learn 模式的物理反馈能否落地。

## 代码落地清单（批准后）

- `parser/`：手势互斥 + 边沿事件输出（P0-1、P0-2）
- `state/`：`ptt_mode`（toggle/hold）区分、断连强制停麦
- `executor/`：`ptt_hold` 动作（P0-2）
- `ui/`：未知报文提示、`doctor` / `debug` / `reload` 命令、延迟标注
- `docs/`：默认行为并存的说明（P0-3 选项定稿后写入 README 与 UI 备注）
