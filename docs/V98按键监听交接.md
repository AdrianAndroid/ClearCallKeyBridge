# V98 按键监听交接（2026-11-19）

## 目标和边界

用户希望在 **macOS** 上监听 V98 的物理按键，并最终用于自定义动作；设备隔离非常重要，因为这是公司管理的 Mac。当前阶段只验证 V98，不能影响键盘、鼠标及其他设备。窗口不置顶。用户后续仍关心 EDIFIER ClearCall 200，但当前实测设备是 V98，两者行为不能混同。

必须遵守仓库 `AGENTS.md`、`CLAUDE.md` 和 `openspec/`；改行为先写 `openspec/changes/` 并同步规范。用户明确要求 macOS；历史 Linux 优先的文档不再适用。不要启用不能区分设备来源的全局媒体键拦截或音量回写，不要伪造按键或释放边沿。

## 最新突破：系统日志能实时区分 V98

2026-11-19 在本机 macOS 15.6.1、V98 在线时，先用 PacketLogger 抓包，再将报文时间与 `bluetoothd` 日志对照，发现系统日志明确包含 V98 蓝牙地址及以下消息：

```text
Received AVRCP Play command from device 41:42:DF:39:9A:BE
Received AVRCP Pause command from device 41:42:DF:39:9A:BE
Received notification for absolute volume 0x1c (~22%) from device 41:42:DF:39:9A:BE
```

已明确验证：**移除 Apple 蓝牙详细诊断描述文件后**，如下只读实时命令仍能收到 V98 的播放、暂停及绝对音量通知。用户依次多次按了播放、音量加和音量减，确实捕获到了对应类型的消息：

```bash
/usr/bin/log stream --style compact --level default \
  --predicate 'process == "bluetoothd" AND eventMessage CONTAINS[c] "41:42:DF:39:9A:BE" AND (eventMessage CONTAINS[c] "AVRCP" OR eventMessage CONTAINS[c] "absolute volume")'
```

此命令在会话中以提升权限运行；**尚未验证应用本身在普通权限、不同启动方式、重启后是否仍能读取**。这是 Apple 系统日志的文本，不保证 API 稳定、延迟或跨 macOS 版本兼容；需要在应用中检测子进程失败、日志不可用和隐私脱敏，不能宣称一定通用。

**播放键：** 日志有 Play / Pause 命令，可据此识别对应媒体命令；抓包中同一连接也观察到 press/release，但实时日志里只观察到命令，不能据此假造释放边沿或支持按住说话。当前 trigger 封闭清单没有 `play:click`，若要加入播放键作为正式触发源，先更新变更提案与规范，不要误映射为 ClearCall 通话键。

**音量键：** 日志提供的是设备绝对音量数值，不是物理按键的直接边沿。实测同一数值可能重复，邻近通知可能交错（如 0x28、0x24 反复出现），暂不能可靠把每条通知转成一次加/减，也不能推断按住/松开；不能仅靠 CoreAudio 全局音量反推来源。下一步需要单独隔开每次操作、记录准确时间、研究去重和基线更新，并测试是否存在系统主动同步、音量边界、快速连按等误判。

## 已验证无效的路径

- V98 在系统中有蓝牙 HID 节点，产品名 `V98`，HID 序列号为设备地址。`scripts/v98_hid_probe.swift` 用名称、地址和 Bluetooth 匹配并直接打开设备，IOKit 原始报告与值回调均未收到用户按键。
- `scripts/v98_corehid_probe.swift` 用 Apple CoreHID 按名称和地址匹配，同样匹配成功但未收到输入报告。两份探针已经过 Swift typecheck。这些结果只表示对应测试未见回调，不证明系统绝对没有其他路径。
- 以前仅观察 CoreAudio 全局音量，虽能看到变化，但无法区分设备来源；早期实现还会回写音量并有误报，不适合本机需求。

## 普通权限三轮实测（2026-11-19 补录）

在移除诊断描述文件、**普通用户权限（非提升）**下完成三轮 `log stream` 实测，设备 V98 在线（地址 `41:42:DF:39:9A:BE`，`system_profiler` 确认）：

| 轮次 | 谓词 | 操作 | 结果 |
|---|---|---|---|
| 1 | 窄谓词（AVRCP/absolute volume） | 播放/暂停/音量+/音量− | **0 条捕获**（首次异常，疑为启动预热/时机问题，未定论） |
| 2 | 宽谓词（仅 bluetoothd + 地址） | 播放/暂停/音量键多轮 | ✅ Play/Pause 命令 + 绝对音量通知全部可见（默认级别 Df） |
| 3 | 窄谓词复测 | 播放×1、音量+×1、键盘媒体键负向 | ✅ 窄谓词可复现捕获；负向测试 **0 条**，设备隔离成立 |

同步确认的事实：

- 普通权限 + 无描述文件即可读取上述消息，**不依赖提升权限**；谓词中 `eventMessage` 在输出头部被显示为 `composedMessage`，两者等价。
- 音量键按一次可产生多条通知（实测单按音量+出现 `0x28`×2 → `0x24`×2 共 4 条），同值重复、邻近值交错均再次出现，与既有结论一致：**不能把每条通知映射为一次按键，方向映射需先做去重与基线逻辑**。
- 用户侧音乐 App 被播放键唤起，说明系统在处理同一命令；自定义动作与系统行为是并存关系。
- 原始捕获仅留在 `/tmp`（v98-wide-round2-backup.log / v98-logstream-*.log），不提交仓库。

## 建议下一步

1. 先提交一份 OpenSpec change：定义 V98 设备专属、只读日志检测通道、用户可见的“已检测/未检测”状态，以及日志不可用的降级行为；保留其他设备不受影响的约束。明确日志监听不是拦截，也不是通用蓝牙协议 API。
2. 单独实现采集模块：异步启动 `/usr/bin/log stream`，在系统谓词及解析层均严格按目标地址过滤；只处理已验证的两类消息。设备地址不应永远硬编码，应从明确的 V98 目标配置读取；未配置、地址不匹配、子进程退出、权限不足时明确显示不可用，不能误判成功。确保退出清理子进程，不阻塞 UI。起初只展示原始检测事件，不执行映射动作。
3. 先验证 **移除描述文件、普通应用权限**下可持续读取 V98 播放和音量通知；再用非 V98 的键盘和鼠标做负向测试，确认不会触发。隔离每个音量操作并覆盖重复、交错、边界、快速连按，再决定何时允许方向映射。
4. 播放键和 PTT 语义须先经规范明确：日志本身没有可靠 release，禁止将其用作 `ptt_hold`；断连、超时和退出仍必须强制停麦。
