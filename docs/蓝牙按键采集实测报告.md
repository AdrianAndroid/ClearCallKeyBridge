# macOS 蓝牙耳机按键采集：实测报告与经验总结

> 项目：ClearCallKeyBridge（漫步者 ClearCall 200 话务耳机按键桥接）
> 机器：Mac mini，macOS 15.7.9（Build 24G830），Apple 内置蓝牙，无外接适配器
> 结论日期：2026-11-19

这份文档记录的是"一轮完整的技术排查"：从系统按键事件，到 HID，到 CoreAudio，到蓝牙协议层，逐条验证，
最后确认为什么**在 macOS 15 上这副耳机的三个物理键在用户态完全不可观测**。
写下来是为了让后来者不用把同样的坑再踩一遍。

---

## 1. 目标

- 设备：EDIFIER **ClearCall 200** 头戴话务耳机（蓝牙 5.0，支持 A2DP / AVRCP / HFP，仅 SBC）
- 物理键：**电源键、音量 +、音量 −、通话键**（共 4 颗，无独立静音键；通话中静音 = 电源键单击）
- 诉求：三个常用键（音量 + / 音量 − / 通话）能被客户端"监听到 + 拦截掉 + 映射成自定义动作"，
  按键时界面对应卡片亮灯。

---

## 2. 结论速览

| 探测通道 | 工具 / API | 结果 |
|---|---|---|
| 系统按键事件 | `CGEventTap`（`cgHIDEventTap` + `cgSessionEventTap` 双层，仅 `type=14`） | 按键期间 **0 条**；抓到的全是鼠标点击（`subtype=7 data1=0x1`） |
| HID 设备枚举 | `hidutil list` / `ioreg -c IOHIDDevice` / `IOHIDManager` | 16 个 HID 设备中 **无 EDIFIER**（只有键盘、鼠标、内置耳机孔线控） |
| HID 报告（Swift 复验） | Swift + `IOHIDManager` + `MPRemoteCommandCenter` | 设备枚举正常，耳机未知；媒体命令 **0 次触发** |
| 音频属性（高频采样） | CoreAudio ctypes，5ms 采样 `volm` elem1/2、`vmvc`、`mute` | 按键期间 **0 条变化** |
| 音频属性（变更通知） | `AudioObjectAddPropertyListener` | 注入音量时可收到回调（验证通道本身可用），但真实按键 **不触发** |
| 蓝牙日志（root） | `log stream --info --debug`（predicate: `bluetoothd`/`bluetoothaudiod`/`coreaudiod`/`mediaserverd`） | 918 行日志中 **0 条** `AVRCP` / `SetAbsoluteVolume` / `volume` |
| AVRCP 控制通道 | `IOBluetooth` L2CAP `PSM 23`（UUID `110F`） | 通道对象可创建，但同步打开返回 **`-536870212`**（被系统独占，无法成为第二个 CT） |
| HFP 通道 | `/dev/cu.EDIFIERClearCall200`、`RFCOMM` 通道 12 | 句柄可打开，45–60 秒 **读取 0 字节**（被 bluetoothd 独占） |
| HCI 抓包 | `defaults write ... HCIEnabled/HCI Logging` + 重启 `bluetoothd` | **无 `/var/log/bluetooth` 目录**，不产生 hci.log（需 Apple PacketLogger 才有抓包能力） |

**一句话结论**：该耳机按键走的是 **AVRCP 绝对音量（Absolute Volume）**，
报文在 `bluetoothd` / `mediaremoted` 内部被消费，不产生任何用户态可见事件；
macOS 13+ 已删除可注入的 `AVRCPAgent` 进程，且系统卷受 **SIP + SSV + hardened runtime** 保护，
第三方既读不到、也拦不住。

## 3. 逐条实验记录

### 3.1 系统按键事件（CGEventTap）

```python
# 曾经的双层 tap（Quartz）
tap = CGEventTapCreate(kCGHIDEventTap, kCGHeadInsertEventTap, kCGEventTapOptionListenOnly,
                       CGEventMaskBit(14), cb, None)
tap2 = CGEventTapCreate(kCGSessionEventTap, ...)
```

- 键盘媒体键（`subtype == 8`）能被 CGEventTap 读到，这是操作系统的标准通路；
- 但按耳机音量键、通话键，**一条都没有**；
- 说明耳机按键**没有走"键盘/媒体键"这条翻译链路**。

### 3.2 HID 枚举

```bash
hidutil list                     # 16 个设备：AppleACPIButton / HP 125 键盘 / USB 光学鼠标 / Headset(内置)
ioreg -c IOHIDDevice | grep -i edifier   # 空
```

- 对照实验：**罗技鼠标能自定义按键**，因为它是 HID 设备，每个键都是一个 HID usage，
  且厂商还用私有页 `0xFF00` 写 feature report 做配置；
- 耳机不是 HID，所以 `IOHIDManager` 这条路对它天然无效——这是**设备类别差异**，不是软件能力差异。

### 3.3 CoreAudio 音频属性

采样脚本（5ms，覆盖 `volm` elem1/2、`vmvc` elem0、`mute`）：

```
volm1 = 0.6000   volm2 = 0.8819   vmvc0 = 0.8819   mute0 = 0.0000
```

按键期间：**无任何变化**。由此纠正了一个此前的误判：

> 早期版本"按一下会亮灯"是**假阳性**——那是程序自己回写音量触发了自己的通知监听，
> 不是耳机按键被识别。

### 3.4 蓝牙日志（root）

```bash
# 早期 nohup 在 do shell script 下失败："can't detach from console"
# 改为双 fork + setsid + execv 才能稳定后台运行
sudo log stream --info --debug --predicate 'process == "bluetoothd"'
```

- 918 行日志里，绝大多数是 `BLE Scanner Device Found: ...` 噪音；
- 过滤 `avrcp|absoluteVolume|passthrough|SetVolume|volume`（排除扫描噪音）→ **0 条**。

### 3.5 AVRCP / L2CAP（IOBluetooth）

```bash
python3 -m pip install pyobjc-framework-IOBluetooth
```

```python
# 关键：同步接口的真实签名（NSError** 出参在前）
ch = dev.openL2CAPChannelSync_withPSM_delegate_(None, 23, delegate)
# => (-536870212, <IOBluetoothL2CAPChannel PSM:23 UUID:110F>)
```

- `PSM 23` + `UUID 110F` 确认是 AVRCP 控制通道；
- 返回码 `-536870212` 表示打开失败——系统已作为 Controller 连接，**一个连接不允许第二个 CT**；
- 这条就是"自己写蓝牙服务去拦命令"在 macOS 上行不通的实证。

### 3.6 HFP / RFCOMM

```bash
ls /Library/Preferences/com.apple.Bluetooth   # PersistentPorts 里：
# FC:E8:06:72:A4:04 = { BSDName = EDIFIERClearCall200; RFCOMMChannel = 12; }
```

- 只有 **RFCOMM 通道 12**（HFP 语音通道），没有 HID；
- 直接 `open("/dev/cu.EDIFIERClearCall200")` 成功，但 45–60 秒 `read` 返回 0 字节。

### 3.7 HCI 抓包尝试

```bash
sudo defaults write /Library/Preferences/com.apple.Bluetooth "HCI Logging" -bool true
sudo defaults write /Library/Preferences/com.apple.Bluetooth "HCIEnabled" -bool true
sudo killall bluetoothd
```

- `defaults read` 确认键值写入成功、`bluetoothd` 已重启、耳机仍连接；
- 但 **`/var/log/bluetooth` 目录不存在**，没有 `hci.log`；
- 结论：这条"官方文档式"的抓包开关在 macOS 15 上不生效，必须用 Apple
  **Bluetooth Explorer / PacketLogger**（Additional Tools for Xcode，需 Apple ID 下载）才有 HCI 抓包能力。

## 4. 为什么不行（原理层）

1. **这款耳机不是输入设备**。它对外暴露的服务只有 `HFP / AVRCP / A2DP / Braille / ACL`，没有 HID。
2. **AVRCP 绝对音量不是"按键事件"**。耳机侧直接把自己认为的音量值写过来，
   系统据此调整音量，链路里没有"上一曲/下一曲/加/减"的语义可供第三方读取。
3. **profile 层被系统独占**。`bluetoothd` 持有 AVRCP 连接，第三方无法同时注册为 Controller。
4. **注入点已消失**。2014 年那类项目靠注入 `AVRCPAgent.app` 的
   `handleIncomingAVRCommand` 实现拦截；macOS 13+ 该进程被并入 `bluetoothd` / `mediaremoted`，
   且运行在签名系统卷（SSV）+ SIP + hardened runtime 下，**无法注入、无法替换**。

## 6. 可行方案与代价

| 方案 | 能区分三个键 | 能真拦截 | 成本 |
|---|---|---|---|
| **A. 换 USB/HID 型耳麦**（Jabra Evolve、Plantronics 等） | ✅ | ✅ | 换硬件；开发约 1 天（`IOHIDManager` 读写 + 映射） |
| **B. USB 蓝牙适配器 + BTstack**（`bluekitchen/btstack`，开源） | ✅ | ✅ | 适配器约 50 元；需 `sudo nvram bluetoothHostControllerSwitchBehavior=never`；开发 3–5 天，且 **A2DP 音频要自行接管**（否则耳机连上适配器后系统就没声音了） |

> BTstack 官方支持 macOS（`port/libusb`），内置 A2DP / AVRCP / HFP / HID，
> 能在用户态跑完整协议栈——这是唯一能"真拦截"的软件路线，代价是音频链路自己搭。

## 8. 踩坑记录（下次少走弯路）

| 坑 | 现象 | 解法 |
|---|---|---|
| `sudo -n` 不可用 | `sudo: a password is required` | 用 `osascript -e 'do shell script ... with administrator privileges'` 弹系统授权框 |
| `nohup` 在授权 shell 下失败 | `nohup: can't detach from console` | 写 Python 双 `fork` + `os.setsid()` + `os.execv()` 自建守护进程 |
| `defaults write com.apple.Bluetooth` 无效 | 写到了 root 的偏好域 | 必须写 `/Library/Preferences/com.apple.Bluetooth`（带全路径） |
| pyobjc 类名 | `objc.lookupClass` 不存在 | 用 `objc.lookUpClass` |
| `IOBluetooth` 同步接口 | `Need 3 arguments` / `argument 0 must be None` | 真实签名是 `openL2CAPChannelSync_withPSM_delegate_(None, psm, delegate)`，`NSError**` 在前且必须传 `None` |
| pyobjc delegate | `does not recognize -conformsToProtocol:` | delegate 必须是 `NSObject` 子类（`objc.lookUpClass("NSObject")`），并用 `@objc.typedSelector` 声明选择子 |
| CoreAudio 假阳性 | 自己 `set_volume` 会触发自己的监听 | 监听回调里要区分"外部改动"与"自己回写"，否则会误判为按键 |
| root 文件清理 | `rm /tmp/btlog.txt` 被拒（root 属主） | `sudo rm`，或改用截断写入 |

## 10. 一句话给后来者

> 在 macOS 上做蓝牙耳机按键驱动，**先确认设备是不是 HID**（`hidutil list`）。
> 是 HID → 走 `IOHIDManager`，能读能吞；
> 不是 HID → 只能走 AVRCP，而 AVRCP 在 macOS 上**没有第三方可用的拦截入口**，
> 要么换设备，要么外接适配器自己跑协议栈。别把时间花在权限、签名、语言上，那些都解决不了设备类别问题。
