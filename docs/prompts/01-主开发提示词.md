你现在负责开发一个单体终端客户端项目：EdifierClearCall200 —— 漫步者 ClearCall 200 话务耳机的按键自定义工具。

## 0. 开工前必做

先按顺序完整读取仓库中这些文件，读完再写任何代码：
1. README.md
2. CLAUDE.md
3. openspec/project.md
4. openspec/specs/ 下 7 个 spec：device-input / state-model / key-mapping / action-execution / learn-mode / terminal-ui / runtime-ops

这些 spec 是项目的唯一事实来源。实现与 spec 冲突一律以 spec 为准；若你认为 spec 有问题，
先告诉我并给出修改建议，等我确认后再改 spec，不允许自行偏离。

## 1. 项目定位（最容易跑偏，务必守住）

- 程序是【单体、单进程、本地运行的终端程序】：蓝牙采集、按键解析、规则管理、状态机、动作执行、ASCII 界面，全在同一个程序里。
- 【OpenSpec 只是模型契约规范文档，不是运行中的服务】，不存在 OpenSpec 进程，不存在 TCP 中枢，不存在 Agent/Worker 分布式拆分。
- 参考体验是 remote-mic-app（PTT 按住说话 + 按键自定义映射），我们额外叠加 HFP 话务状态显示。
- 目标平台：Linux（BlueZ / btmon）优先；macOS 只预留适配入口，MVP 不实现。

## 2. 硬件与触发源（固定，不可自由增删）

设备：漫步者 ClearCall200，蓝牙 5.0，A2DP/AVRCP/HFP，Type-C 仅充电（无 USB HID、无 USB 音频）。

7 个可绑定触发源（来自 4 个物理按键）：
mute:click    静音键单击     仅 HFP 通话 active 时耳机才上报，空闲按大概率无报文
call:click    通话键单击
call:long     通话键长按
call:double   通话键双击
volp:click    音量+ 单击
volp:long     音量+ 长按     AVRCP，最稳定
volm:click    音量- 单击

power 电源键：不纳入触发源，只做链路生命周期。

关键硬件行为（不要试图"修复"）：
- mute 在空闲状态不上报，是耳机固件行为，程序如实反映（界面备注 + 学习模式下无反馈），禁止软件伪造事件。
- 支持一拖二，HFP 链路会切换，解析要按连接句柄区分。

## 3. 状态模型

app_mode  : normal | learn
call_state: idle | ringing | active | held | dialing
mic_mute  : 0 / 1
ptt_state : 0 / 1
device_online, learn_remain, busylight_capable（见 state-model spec）

## 4. 动作集合（MVP 只这 5 个）

ptt_toggle          切换 PTT 虚拟麦克风（按一下开、再按一下关）
ptt_hold            按住说话：press 开麦、release 停麦（对标 remote-mic-app 手感）
hid_send F13        发送 HID 键码
obs_toggle_mute     OBS WebSocket 静音切换
notify"文本"         系统桌面通知

MVP 不做：shell 脚本、zoom/teams 静音、多动作串联、条件分支、组合按键、多套配置。
一条 trigger 只绑定一个 action。

关键约束：
- 推流区分 ptt_mode（toggle / hold），不得叠加；设备断连、release 丢失（超 ptt_hold_max_sec）、程序退出都必须强制停麦。
- PTT 输入源取 actions.ptt.source（default / headset），设备不在则 ERR 并停麦。
- AVRCP 音量/媒体键的默认行为拦不住（决策 A：并存），自定义动作与系统行为同时发生；
  代码与文案都不得自称"已拦截"，推荐把自定义优先绑到 volp:long / volm:click / call:long。
- 单击判定时延：只有该键**绑定了 double 规则**才等 double 窗口；未绑定则 release 立即判定；长按到阈值即时触发，且不再产 click。
- parser 需额外产出内部边沿事件 edge press / edge release（不进 UI 事件流），供 ptt_hold 使用；断连时补发 release。

## 5. 学习/测试模式（本项目重点功能）

- `learn` 进入：继续采集、继续刷新状态栏，但【完全不执行任何绑定动作】（跳过规则匹配）。
- 识别成功输出：`> [LEARN ✅] trigger=call:click        → BusyLight blink ✨`，并尝试让耳机忙灯闪一下。
- 忙灯不可控时降级：`> [LEARN ✅] trigger=xxx        → BusyLight control unsupported`，不重试不报错。
- 30 秒自动超时回 normal，也可 `normal` 手动退出。
- learn 不写入规则，只做检测。

## 6. ASCII 界面（无 Web、无 GUI）

顶部状态栏：
📞 CALL: [IDLE] | MIC: [OPEN] | PTT: [OFF] | MODE:[NORMAL]
learn 时状态栏下加：
⚠️ LEARN MODE ACTIVE: 按键只会检测、不执行动作 | 30s auto exit

自上而下：状态栏 → 触发源列表（带序号和硬件限制备注）→ 规则表 → 事件流（最多 200 行）→ 命令提示符 `> _`

输出行前缀只允许：
> EVENT trigger=... / > ACTION action=... / > STATE call_state=.. mic_mute=.. /
> [LEARN ✅] ... / > OK ... / > ERR ... / > MODE ...

必须实现的命令：
list / set N ACTION / learn / normal / test TRIG / save / reload / state / doctor / debug on|off / export feed / help / quit
（test 用于无蓝牙时手动模拟事件调试界面，格式 `test trigger=volp:long`；
 doctor 做环境自检；--log <path> 支持事件流落盘）

## 6.1 运行期约束
单实例锁（$XDG_RUNTIME_DIR/clearcall200.lock，陈旧锁自动接管）；quit / SIGTERM / SIGINT 统一清理
（停采集 → 停推流 → 销毁 uinput → 恢复终端 → 删锁）；外部改动 rules.json 只提示不静默重载。

## 7. 模块划分（不要堆进一个文件）

bluetooth/    BlueZ / btmon 采集与报文解析（独立线程，不阻塞 UI）
parser/       按键时序解析：单击 / 长按 / 双击，防抖，阈值可配
rules/        规则表加载、修改、持久化（JSON）
state/        全局状态机 + learn 倒计时
executor/     4 个动作实现，异常隔离
ui/           ASCII 渲染，≤10Hz 合并刷新，非 TTY 降级为纯文本日志
busylight/    忙灯能力探测 + 闪烁，失败降级

## 8. 开发顺序（严格按这个节奏，一步一交付）

分 3 批交付（依据是依赖边界，不是功能模块）：
批 1  整机可跑 —— 骨架 + 状态机 + 规则 + ASCII 界面 + 全部命令 + 单实例锁 + doctor 骨架
               （不接蓝牙，全部用 test 命令模拟事件；动作先占位）
批 2  硬件接入 —— 蓝牙采集 + parser（手势判定 / 边沿事件）+ 学习模式 + 忙灯探测（需抓包）
批 3  执行器 + 收口 —— 5 个动作真实落地 + 异常路径 + 性能 + spec 对账（需权限/OBS）

每批交付时程序都必须是"可运行 + 可验收"的完整状态；不要交半成品，也不要跨批实现。
每批结束后输出：改动文件清单、验收勾选结果、遗留项与下一批建议。

每步开始前先说明"本次开发哪个模块、要新增哪些文件"，我确认后再写代码。
