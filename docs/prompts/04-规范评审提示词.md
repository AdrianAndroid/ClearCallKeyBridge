# 提示词 04 · 规范评审与修订提示词

> 用途：改需求时用。原则：**先改 spec，再改代码**。

## A. 规范自检（拿到 AI 产出后校验用）
```
对照 openspec/specs/ 的 7 份 spec，逐条检查当前代码：
1. 列出每条 Requirement / Scenario 的实现状态：已实现 / 部分实现 / 未实现 / 偏离。
2. 偏离项要指出具体代码位置与 spec 原文，并说明是代码错还是 spec 不合理。
3. 不要顺手修改代码，先只给报告，等我确认改哪边。
输出格式：表格（capability | requirement | 状态 | 证据/差异说明）。
```

## B. 新增功能时的规范修订
```
我想给项目加一个功能：<描述>。
请按 OpenSpec 流程走：
1. 判断它属于哪个 capability（device-input / state-model / key-mapping / action-execution / learn-mode / terminal-ui），还是需要新建 capability。
2. 在 openspec/changes/ 下新建一个变更提案 md：背景、动机、影响面、是否需要改状态模型、是否破坏现有术语。
3. 给出 spec 的 diff（用 ## ADDED / ## MODIFIED / ## REMOVED Requirements 的方式），只改文本，不写代码。
4. 明确指出这次改动会影响到哪些模块与哪些已有 Scenario。
先只出提案与 diff，等我批准再落地代码。
```

## C. 硬件行为存疑时的调研提示词
```
关于 ClearCall200 的按键行为我有疑问：<问题>。
请先不要改代码，给我：
1. 需要用 btmon / Wireshark 抓哪几类报文、过滤表达式怎么写。
2. 期望看到的报文特征与判读方法。
3. 如果实测与 spec 假设不一致，spec 哪一条需要改、怎么改。
```
